## 1. Цель

Приложение ведёт планы приёма **любых** лекарств: на каждое лекарство свой раздел со своими планами, а домашний экран и аналитика строятся универсально поверх всех разделов сразу.

Механизм Акнекутана (блоки, чередование доз, кумулятивная доза, мг/кг) должен остаться **лучшим** в системе, а не быть срезанным до среднего случая.

### Ключевой вывод по текущему боту

Модель данных бота уже универсальна. `plans.schedule_json` + `plan_intakes(plan_id, day_num, medication_id, status, dose_mg, taken_at)` — это правильная форма. Акнекутан-специфичны не схема, а точки хардкода (раздел 11). Проект = снятие хардкодов + перенос UI, а не переписывание.

### Имена и идентификаторы

Зафиксированы, чтобы имя не всплыло как решение в середине разработки.

| Что | Значение |
|---|---|
| Название в App Store | Мои Лекарства — дневник приёма |
| `CFBundleDisplayName` (под иконкой) | Приём |
| Репозиторий | `mymeds-ios` |
| Xcode target / Swift module | `MyMeds` |
| Bundle ID | `com.l1ratch.mymeds` |
| App Group | `group.com.l1ratch.mymeds` |
| Widget extension target | `MyMedsWidget` |
| Файл базы | `mymeds_data.json` + `mymeds_data.bak` |
| Формат плана | `medplan/1` — намеренно без бренда (раздел 4) |

Три разных имени — не избыточность, а три разных ограничения. Название в сторе длинное и описательное, потому что по нему ищут. Подпись под иконкой короткая, потому что iOS режет её примерно на 6 символах и «Мои Лекарства» превратилось бы в «Мои Лек…». Идентификатор в коде — валидный Swift-символ без коллизий со стандартной библиотекой.

Осознанный риск имени: раздел «Лекарства» уже есть во встроенном приложении Здоровье (iOS 16+) — с расписанием, напоминаниями и отметкой приёма. Отличие этого приложения не в перечне лекарств, а в механизме курса: чередующиеся схемы доз, кумулятивная доза к цели 120–150 мг/кг, цепочка блоков, правка дозы конкретного дня без потери истории, отчёт врачу. Это же — основа текста для стора.

Название препарата в имени приложения не используется: `Акнекутан` — чужой товарный знак и триггер ревью по guideline 1.4.1 (раздел 11).

## 2. Что не строим (осознанно)

| Не строим | Почему |
|---|---|
| Бэкенд, API, авторизацию | Напоминания локальные; врачу хватает PDF/CSV через share sheet |
| HealthKit | В нём нет домена лекарств и адгереции, интегрировать нечего |
| Движок плагинов под типы лекарств | Покрытие даёт «значение + единица», не подсистема расширений |
| DSL расписания в хранилище | Правила живут только в авторинге конструктора, на диске — развёрнутая сетка по дням |
| Конвертер единиц | Суммируем только внутри одинаковых `unit` |
| Android | Сейчас не пишем; страховка — платформенно-нейтральный JSON-контракт (раздел 4) |
| Dock (TabView) | Один главный экран + настройки сверху; экраны независимы от корня — вернёмся, когда появятся 3+ равноправных экрана (раздел 12) |
| Справочник лекарств | Это контентный проект. Свободный ввод названия + дефолты на лекарство |
| Состояния плана `active/future/completed` | Вычисляются из дат, не хранятся (раздел 5) |
| Автопропуск как запись в БД | Вычисляется при чтении (раздел 6) |

## 3. Модель данных

Три сущности. Всё остальное — производное.

```swift
struct Medication: Codable, Identifiable {
    let id: UUID
    var name: String              // "Акнекутан", "Витамин E", "L-тироксин"
    var form: String?             // "капсулы 8 мг", "таблетки 50 мкг"
    var unit: DoseUnit            // .mg .mcg .iu .tablet .capsule .ml .drop
    var intakeRule: String?       // "во время ужина, с жирной пищей" — свободный текст
    // Необязательные оверлеи. Пустые → аналитика их не показывает;
    // принятая кумулятивная доза считается в любом случае (раздел 7).
    var cumulativeTarget: Double? // мг на весь курс (изотретиноин: 120–150 мг/кг); nil = чёткой цели нет
    var weightKg: Double?         // для отображения мг/кг/день
    var notifyWindow: NotifyWindow? // окно напоминаний — НА лекарство; nil = напоминаний нет
    var colorHex: String?
    var createdAt: Date
}

struct Plan: Codable, Identifiable {
    let id: UUID
    var medicationId: UUID
    var name: String              // "Блок 1", "Курс осень 2026"
    var startDate: CivilDate?     // nil = ещё не начат, на home не появляется
    var durationDays: Int         // > 0
    var schedule: [Int: DaySlot]  // 1...durationDays → что принять в этот день плана
    var stoppedAt: CivilDate?     // явная ранняя остановка курса (отменил врач)
    var createdAt: Date
    var updatedAt: Date
}

struct DaySlot: Codable {
    var dose: Double              // СУММАРНАЯ доза за день в unit лекарства; 0 = день без приёма
    var times: Int                // приёмов в день — только для отображения; отметка всегда одна на день (раздел 13.2)
}

struct Intake: Codable, Identifiable {
    let id: UUID
    var planId: UUID
    var day: Int                  // 1...durationDays
    var status: Status?           // nil = отметки нет (но доза могла быть перекрыта)
    var actualDose: Double?       // фактически принятая доза
    var takenAt: Date?
    var doseOverride: Double?     // ручная правка плановой дозы ДО отметки
    enum Status: String, Codable { case taken, skipped }
}

struct NotifyWindow: Codable {
    var startHour: Int            // 20
    var endHour: Int              // 23
    var intervalMinutes: Int      // 30
}

/// Дата без времени и таймзоны; в JSON — строка "YYYY-MM-DD" (custom Codable).
/// Номер дня = разница календарных дней в Calendar.current + 1 — чистая арифметика
/// по (year, month, day), DST и перелёты на неё не влияют. Моменты времени
/// (`takenAt`) в вычислении дня не участвуют.
struct CivilDate: Codable, Equatable, Comparable {
    var year: Int
    var month: Int
    var day: Int
}
```

**Инварианты** (проверять при импорте и при сохранении плана):

- `durationDays > 0`; ключи `schedule` ⊆ `1...durationDays`.
- `dose >= 0`. `dose == 0` — легальный «день без приёма» (окна между блоками).
- `Intake.day` ∈ `1...plan.durationDays`; одна запись на `(planId, day)` — уникальность.
- `status != nil` ⇒ `takenAt != nil`.
- `actualDose` при проставлении `status` наследует `doseOverride ?? schedule[day].dose` (правило из `DECISIONS.md` 2026-08-25, сохраняется).
- Сброс отметки обнуляет `status`/`takenAt`/`actualDose`, но **сохраняет** `doseOverride` (правило `delete_plan_intake`, сохраняется).
- Редактирование плана: пока не начат — любое; **после старта** — только `name`, `doseOverride` дня и `stoppedAt`. Структурные правки (`durationDays`, форма расписания) — только новым планом: иначе `Intake.day` повиснут за новой границей.
- Пересечение диапазонов двух планов одного лекарства разрешено (home показывает оба, оба идут в кумулятивную дозу), но при сохранении UI предупреждает о пересечении.

### Отличие от бота

`plan_intakes.medication_id` исчезает: план принадлежит одному лекарству, `main`/`additional` больше нет. Псевдостатус `not_marked` распадается на честные `status == nil` + `doseOverride`. `auto_skipped` не хранится (раздел 6).

## 4. JSON-контракт плана (переносимость)

Единственная настоящая страховка на Android — этот файл. Он же формат импорта/экспорта и формат обмена с врачом.

```json
{
  "format": "medplan/1",
  "medication": {
    "name": "Акнекутан",
    "unit": "mg",
    "form": "капсулы 8 мг",
    "intakeRule": "во время ужина, с жирной пищей",
    "cumulativeTarget": 8500,
    "weightKg": 68,
    "notifyWindow": { "startHour": 20, "endHour": 23, "intervalMinutes": 30 }
  },
  "plan": {
    "name": "Блок 1",
    "startDate": "2026-05-17",
    "durationDays": 28,
    "schedule": {
      "1":  { "dose": 8,  "times": 1 },
      "2":  { "dose": 16, "times": 1 },
      "22": { "dose": 16, "times": 1 },
      "28": { "dose": 24, "times": 1 }
    }
  }
}
```

Правила:

- `format` обязателен и версионируется. Неизвестная мажорная версия → отказ с внятным сообщением, не тихий дефолт.
- Дата — ISO-8601 `YYYY-MM-DD`. Время — ISO-8601 с таймзоной.
- `unit` — строка из закрытого списка `mg|mcg|iu|tablet|capsule|ml|drop`. Неизвестная единица → ошибка импорта (не молчаливый `mg`).
- Развёрнутая сетка по дням, **без DSL**. Конструктор на устройстве умеет строить её из правил вида `7:24;14:32;7:32/40`, но наружу всегда отдаёт развёртку — так же, как сейчас делает `constructor.html`. Никакого парсера правил в рантайме.
- Импорт идёт через черновик с предпросмотром и явным подтверждением (правило из `DECISIONS.md` 2026-08-10, сохраняется).
- Отдельный файл = один план одного лекарства. Несколько планов = несколько файлов или архив.
- Полный бэкап данных — собственный корневой маркер `"format": "mymeds-backup/1"` (раздел 9). Импорт различает форматы по маркеру: `medplan/1` → черновик с предпросмотром; `mymeds-backup/1` → полное восстановление с подтверждением (замена, не слияние; `.bak` пишется заранее).

`// ponytail:` один план на файл — потолок на «импортировать 10 планов разом». Понадобится — добавить `medplan-bundle/1` со списком, формат элемента не менять.

## 5. Ядро: резолв дня и агрегация домашнего экрана

Единственное архитектурное отличие от бота. Сейчас бот может путать `day_num` и календарную дату, потому что активный план ровно один. При нескольких лекарствах с разными датами старта это разные вещи, и **home обязан строиться от календарной даты**.

Вся агрегация — одна чистая функция:

```
entries(on: date) -> [Entry]
    for plan in plans where plan.startDate != nil:
        if plan.stoppedAt != nil and on > plan.stoppedAt: continue   // stoppedAt включительно
        n = daysBetween(plan.startDate, date) + 1      // 1-based, календарные дни
        if n < 1 or n > plan.durationDays: continue
        slot = plan.schedule[n]
        if slot == nil or slot.dose == 0: continue     // день без приёма
        Entry(plan, medication, day: n, slot, date)
```

`Entry` — единица всего: одна строка «Сегодня», одна клетка календаря, одна точка heatmap, один элемент знаменателя адгереции, одно уведомление.

Из неё получается всё остальное, без отдельной логики на лекарство:

- **Сегодня** = `entries(on: .now)` + статус каждой.
- **Календарь** = `entries(on: d)` для видимого диапазона.
- **Раздел лекарства** = `entries` с фильтром по `medicationId`.
- **Аналитика** = свёртка по `entries` (раздел 7).
- **Уведомления** = `entries` на ближайшие N дней → `notifyWindow` (раздел 8).

### Состояние плана — вычисляемое

Храним только `startDate`, `durationDays`, `stoppedAt`. Тогда:

| Условие | Значение |
|---|---|
| `startDate == nil` | не начат (черновик) |
| `today < startDate` | будущий |
| `startDate <= today <= lastDay` | активный |
| `today > lastDay` | завершён |

где `lastDay = min(startDate + durationDays - 1, stoppedAt ?? ∞)`. Остановленный план остаётся активным до `stoppedAt` включительно, а не исчезает мгновенно — иначе вместе с ним пропадут уже сделанные отметки последних дней.

**Следствие:** автоматическая промоуция `future → active` (`auto_complete_and_activate_next`) не нужна вообще — план сам появляется на home в свою дату и сам исчезает. Это минус одна подсистема планировщика и минус состояние, которое может рассинхронизироваться.

Для поведения «следующий блок стартует в день завершения предыдущего» не нужна зависимость между планами: UI при сохранении будущего плана предлагает «старт сегодня / завтра / выбрать дату». `startDate` остаётся обычной датой.

### Эталонная реализация правила

Семантика зафиксирована исполняемым кодом — чтобы Swift-порт сверялся с ней, а не с пересказом.

```python
"""Эталон резолва дня. Семантика для Swift-порта; не продуктовый код."""
from dataclasses import dataclass
from datetime import date

@dataclass
class Plan:
    id: str
    medication_id: str
    start: date | None      # None = не начат
    duration: int
    schedule: dict[int, float]   # day -> dose; 0 или отсутствие = день без приёма
    stopped_at: date | None = None

@dataclass
class Entry:
    plan_id: str
    medication_id: str
    day: int
    dose: float
    on: date

def entries(plans: list[Plan], on: date) -> list[Entry]:
    """Все элементы приёма, назначенные на календарную дату `on`."""
    out: list[Entry] = []
    for p in plans:
        if p.start is None:
            continue
        if p.stopped_at is not None and on > p.stopped_at:
            continue                       # stoppedAt включительно
        n = (on - p.start).days + 1
        if n < 1 or n > p.duration:
            continue
        dose = p.schedule.get(n, 0)
        if dose <= 0:
            continue                       # день без приёма
        out.append(Entry(p.id, p.medication_id, n, dose, on))
    return out


def _ids(es: list[Entry]) -> set[str]:
    return {e.plan_id for e in es}


def _selftest() -> None:
    akn = Plan("p1", "akn", date(2026, 5, 17), 28,
               {d: (8 if d % 2 else 16) for d in range(1, 29)})
    vitd = Plan("p2", "vitd", date(2026, 6, 1), 90, {d: 2000 for d in range(1, 91)})
    stopped = Plan("p3", "ab", date(2026, 5, 1), 30, {d: 1 for d in range(1, 31)},
                   stopped_at=date(2026, 5, 10))
    draft = Plan("p4", "x", None, 10, {d: 1 for d in range(1, 11)})
    gap = Plan("p5", "y", date(2026, 5, 1), 10, {**{d: 5 for d in range(1, 11)}, 2: 0})
    ps = [akn, vitd, stopped, draft, gap]

    # 1. Разные даты старта склеиваются по календарной дате, а не по day_num.
    got = {(e.plan_id, e.day) for e in entries(ps, date(2026, 6, 1))}
    assert got == {("p1", 16), ("p2", 1)}, got

    # 2. До старта второго плана в агрегации только первый.
    day = entries(ps, date(2026, 5, 31))
    assert _ids(day) == {"p1"}, _ids(day)
    assert {e.day for e in day} == {15}

    # 3. Черновой план не появляется никогда.
    for d in (date(2026, 5, 5), date(2026, 6, 1), date(2026, 12, 1)):
        assert "p4" not in _ids(entries(ps, d)), d

    # 4. Остановленный план даёт элементы только до stoppedAt включительно.
    assert _ids(entries(ps, date(2026, 5, 10))) == {"p3", "p5"}
    assert _ids(entries(ps, date(2026, 5, 11))) == set()
    assert _ids(entries(ps, date(2026, 5, 20))) == {"p1"}

    # 5. День с нулевой дозой элемента не даёт; соседние дни дают.
    assert entries([gap], date(2026, 5, 2)) == []
    assert [e.dose for e in entries([gap], date(2026, 5, 1))] == [5]
    assert [e.dose for e in entries([gap], date(2026, 5, 3))] == [5]

    # 6. Границы диапазона плана.
    assert [e.day for e in entries([akn], date(2026, 5, 17))] == [1]
    assert [e.day for e in entries([akn], date(2026, 6, 13))] == [28]
    assert entries([akn], date(2026, 5, 16)) == []
    assert entries([akn], date(2026, 6, 14)) == []

    # 7. После завершения всех планов — пусто.
    assert entries(ps, date(2026, 12, 1)) == []

    # 8. Доза берётся из сетки дня, а не из дефолта.
    assert [e.dose for e in entries([akn], date(2026, 5, 17))] == [8]
    assert [e.dose for e in entries([akn], date(2026, 5, 18))] == [16]

    print("selftest OK")

if __name__ == "__main__":
    _selftest()
```

**Проверено:** 8 групп assertion'ов, все проходят (`python _akn/day_resolver_reference.py` → `selftest OK`; повторено после правок v2). Каноническая копия одна — `_akn/day_resolver_reference.py`; `spec_block_check.py` — её дубликат, не форкать семантику по двум файлам. Это не иллюстрация, а исполняемое определение правила. Swift-порт: номер дня — разница `CivilDate` в `Calendar.current`, без арифметики по timestamp.

## 6. Статусы отметок

Храним только факт действия пользователя. Всё остальное выводится.

| Состояние | Как получаем |
|---|---|
| `taken` | запись есть, `status == .taken` |
| `skipped` | запись есть, `status == .skipped` (пользователь явно нажал «пропустил») |
| **`missed`** | записи нет или `status == nil`, **и** `entry.date < today` — вычисляется при чтении |
| `pending` | `entry.date == today`, отметки нет |
| `scheduled` | `entry.date > today` |

**Автопропуск больше не пишется в базу.** В боте `auto_skip_check` в 23:59 создавал строку `auto_skipped`. На устройстве надёжно выполнить код в назначенную минуту нельзя (BGAppRefreshTask оппортунистический, silent push требует сервер). Поэтому:

- `missed` — чисто производный статус. Нулевой планировщик, ноль записей, ноль `reminder_log`.
- Корректно даже если телефон был выключен неделю: при открытии все прошедшие неотмеченные дни сразу `missed`.
- Сохраняется семантика бота (`DECISIONS.md` 2026-08-10): пропуск считается в статистику пропусков, но **не является фактической отметкой** — день остаётся редактируемым, и более поздняя отметка его перезаписывает.
- Отличие от бота, которое надо принять: «пропустил сам» и «забыл отметить» различимы (`skipped` vs `missed`). Это лучше, чем один `auto_skipped`, и в отчёте врачу разделяется.

`// ponytail:` производный `missed` означает, что «день закрыт» нельзя узнать без пересчёта. Держать резолв чистой функцией и кэшировать только на время рендера; понадобится постоянная отметка — не добавлять её, пока не упрутся в производительность.

## 7. Универсальная аналитика

Два слоя: общий (работает для любого лекарства) и оверлей Акнекутана (показывается только если заполнены поля).

### Общий слой — считается по `[Entry]`

| Метрика | Формула |
|---|---|
| Адгереция | `taken / (taken + skipped + missed)` за период. Знаменатель — только прошедшие дни |
| Соблюдение сегодня | `taken / total` элементов за сегодня |
| Streak | цепочка дней **с entries**, где **все** элементы `taken`. Дни без entries (окна между блоками) цепочку не рвут и в неё не считаются |
| Пропуски | `count(missed)` и `count(skipped)` раздельно |
| Прогресс плана | `elapsedDays / durationDays` |
| Heatmap | стиль GitHub: квадрат на каждый календарный день, интенсивность = доля `taken` за день (градации: нет приёма / 0 / <⅓ / <⅔ / всё принято), tap — детали дня |
| Кумулятивная доза | `sum(actualDose where taken)` — **за план** и **за лекарство по всем его планам**. Показывается всегда, цель не требуется. Только внутри одной `unit`; разные единицы никогда не складываются |
| Среднее время отметки | медиана `timeOfDay(takenAt)` |

Домашняя аналитика = те же метрики поверх объединения всех разделов, элемент = `(plan, day)`. «5 из 7 сегодня» — это item-level счёт, он честен и для одного лекарства, и для пяти.

### Оверлей (показывается, только если поля заполнены)

| Метрика | Требует | Формула |
|---|---|---|
| % от цели | `cumulativeTarget` | кумулятивная доза лекарства (общий слой) как % от цели. Цели нет — сама кумулятивная доза всё равно считается и показывается |
| мг/кг/день | `weightKg` | `dose / weightKg` |
| Прогноз завершения | `cumulativeTarget` | остаток / средняя доза за последние 14 дней |

Это ровно то, что делает механизм Акнекутана ценным. Для витамина D поля пустые — блок просто не рендерится. Никаких «плагинов под препарат».

### Чего в боте не было

`get_plan_stats` и `get_total_taken_dose_all_time` фильтруют `medication_id='main'` — дополнительные лекарства в статистику **не попадают вообще**. Поэтому общая аналитика — новая фича, а не перенос. Это самая содержательная часть работы после резолва дня.

## 8. Уведомления на iOS

Здесь бот не переносится, а заменяется. Два жёстких ограничения платформы.

**Ограничение 1: 64 отложенных локальных уведомления на приложение.** Текущая модель «окно 20:00–23:00 каждые 30 минут» = 7 штук в день на лекарство. Три лекарства × неделя = 147. Лимит вылетает сразу.

Решение — **скользящее окно**:

- Планируем только ближайшие **3 дня** (настраиваемо), не весь курс.
- Перевзводим при: запуске приложения, выходе на foreground, отметке приёма, reload виджета.
- Перед планированием отменяем все pending и пересчитываем из `entries` — идемпотентно, без состояния «что уже запланировано».
- Бюджет: `64 / (3 дня × лекарств)`. При нехватке — сокращать интервал окна, а не число дней; предупреждать пользователя в настройках.

**Ограничение 2: отметка из уведомления.** Кнопки «Принял» / «Пропустил» на уведомлении требуют записать данные, пока приложение не запущено. Нужны:

- **App Group** `group.com.l1ratch.mymeds` — общий контейнер приложения, виджета и обработчика действий.
- **Intent Handler** (App Intents) для кнопок уведомления.

⚠️ Прямое следствие для хранения: `mymeds_data.json` должен лежать **в контейнере App Group**, а не в `Documents`, как сейчас в `UnicTracker/Services/StorageService.swift`. Паттерн переиспользуем, путь меняем.

**Гибкость на лекарство:** окно (старт/конец), интервал, вкл/выкл — свои на каждое лекарство (`Medication.notifyWindow`, nil = выкл); горизонт в днях — один глобальный (`Settings.notifyHorizonDays`, дефолт 3). В настройках каждое лекарство показывает «занимает X из 64 слотов». `// ponytail:` горизонт глобальный; понадобится per-med — перенести поле в `NotifyWindow`, планировщик не изменится.

**Протокол записи общего файла.** У JSON три участника: приложение, Intent Handler (отметка из уведомления), виджет (только чтение). Единственный писатель — `StorageService`: все мутации через него, с `NSFileCoordinator` на контейнере App Group и атомарной заменой (temp-файл + `replaceItemAt`). Intent Handler вызывает тот же `StorageService`. Виджет не пишет ничего; при ошибке парсинга показывает последний удачный снимок или пустое состояние.

**Что исчезает вместе с сервером:** `scheduler.py`, `reminder_log`, `auto_skip_check`, systemd-юниты, IPv6-хаки `AiohttpSession`, ежедневный бэкап базы в Telegram. Локальные уведомления срабатывают при закрытом приложении — сервер для напоминаний не нужен.

**Что теряем по-настоящему:** доступ врача read-only и синк между устройствами. Оба закрываются экспортом (раздел 9), синк — позже CloudKit, если появится второе устройство.

## 9. Хранение

Переиспользуем готовый паттерн из `UnicTracker`: `Codable`-корень + один JSON-файл + `.bak` + экспорт/импорт. Ноль новых зависимостей.

```swift
struct AppData: Codable {
    var format: String            // всегда "mymeds-backup/1" — маркер для импорта (раздел 4)
    var version: Int              // схема миграций
    var medications: [Medication]
    var plans: [Plan]
    var intakes: [Intake]
    var settings: Settings
    var exportedAt: Date
}

struct Settings: Codable {
    var notifyHorizonDays: Int    // дефолт 3 (раздел 8). Пока всё — поля добавлять по мере надобности, не про запас
}
```

- Путь: `mymeds_data.json` в контейнере `group.com.l1ratch.mymeds` (раздел 8), не `Documents`.
- Бэкап: `mymeds_data.bak` перед каждой перезаписью, как сейчас в `StorageService`; запись атомарная (temp + `replaceItemAt`), согласование через `NSFileCoordinator` (раздел 8).
- Экспорт: тот же JSON через share sheet + отдельный PDF-отчёт для врача.
- Импорт/восстановление: `medplan/1` — через черновик с предпросмотром и подтверждением; `mymeds-backup/1` — полная замена данных после подтверждения (закрывает сценарий «потерял телефон»).

`// ponytail:` перезапись всего файла на каждую отметку — O(n). При 3 приёмах в день за 5 лет это ~5500 записей и ~1 МБ, то есть незаметно. Упрёмся (или понадобится запросная аналитика по годам) — переход на GRDB/SwiftData **без изменения модели**, только слой доступа. Не делать этого заранее.

`// ponytail:` синка нет. Когда появится второе устройство — CloudKit поверх этого же `AppData`, но помнить ограничения: все связи optional, без unique-констрейнтов, delete rule только `.nullify`. Сейчас под это не проектируем.

## 12. Экраны, навигация и UI-архитектура

### Навигация

Один главный экран — **Home / Сегодня** (корень `NavigationStack`). Настройки — кнопка-шестерёнка в верхней панели, прочее — push/sheet с Home. Dock (TabView) **сейчас не строим**, но каждый экран — самодостаточный корень, не сцепленный с Home: добавление дока позже = обернуть экраны в `TabView` без переписывания. Условие возврата к док-бару: 3+ равноправных направления, между которыми пользователь ходит постоянно.

### Структура приложения (модули с этапа 1)

| Модуль | Содержимое |
|---|---|
| `MyMedsCore` — локальный SPM-пакет | Модель, резолв `entries(on:)`, `StorageService`, кодеки `medplan/1` и `mymeds-backup/1`, планировщик уведомлений. Без SwiftUI. Общий для app, виджета и Intent Handler — поэтому пакет с первого дня, а не «вынесем потом» |
| `DesignSystem` — переиспользование из `UnicTracker` | GlassCard, GlassButton, GlassProgressRing, MeshGradientBackground + `Motion.swift` — единый набор токенов анимаций (спринги, длительности, переходы). Любая анимация в приложении — только через токены; никакого ad-hoc `.animation(...)` внутри экранов |
| `MyMeds` — app target | Только экраны: бизнес-логика в `MyMedsCore`, внешний вид в `DesignSystem` |

Одинаковые элементы (ячейка дозы, карточка лекарства, бейдж статуса, квадрат heatmap, кнопка отметки, маскот) строятся **одним** компонентом с конфигурацией, а не копируются по экранам. Правило: вторая копия UI-элемента = немедленный вынос в общий компонент.

### Экраны

| Экран | Источник данных |
|---|---|
| **Home / Сегодня** (корень) | `entries(on: .now)` по всем лекарствам + сводная адгереция + маскот |
| **Календарь** | `entries(on: d)` по диапазону, GitHub-heatmap |
| **Разделы** — список лекарств, сегмент «активные/архив» | `medications` + производный статус планов; архив = завершённые планы (производно из дат, без отдельного экрана) |
| **Раздел лекарства** | его планы, прогресс, кумулятивная доза (за лекарство и за каждый план), история |
| **План** | дневная сетка, отметки, правка дозы дня |
| **Конструктор плана** | 3 уровня (ниже); выход — развёрнутая сетка + предпросмотр `medplan/1` |
| **Аналитика** | свёртка по `entries` + оверлеи + heatmap |
| **Настройки** (кнопка сверху Home) | окна уведомлений по лекарствам + бюджет «X из 64», горизонт дней, экспорт/импорт/восстановление |
| **Виджет / Live Activity** (`MyMedsWidget`) | `entries(on: .now)` из App Group, только чтение |

### Конструктор плана — 3 уровня

Многофункциональный, но простой за счёт progressive disclosure: уровни — переключатель над одним и тем же черновиком, выход всегда один — развёрнутая дневная сетка (без DSL на диске, раздел 4).

1. **Простой** — название, старт, длительность, одинаковая доза каждый день или «без приёма».
2. **Режим** — чередование доз (`8/16`, правила вида `7:24;14:32` — только авторинг), дни без приёма, ручная правка развёрнутой сетки по дням.
3. **Про** — параметры лекарства: единица, форма, правило приёма, окно уведомлений, кумулятивная цель, вес; предпросмотр JSON `medplan/1`, импорт файла.

### Маскот (streak)

Зверёк/огонёк на Home — **визуализация streak** (раздел 7), ничего больше. Состояние выводится из текущего streak: `0` — грустный/потух, `1–6` — жив, `7/30/100` — уровни огня. Без хранения, без новых сущностей; анимации — из токенов `Motion.swift`.

`// ponytail:` настроения/квесты/магазин маскота = уже не визуализация streak. Не добавлять состояние, пока не попросят.

## 13. Открытые вопросы и риски

1. **Резолв дня должен стать unit-тестом приложения, а не остаться в спеке.** `_selftest` (раздел 5) — единственное место, где семантика агрегации определена точно. Swift-порт обязан перенести его один в один как первый тест проекта. Если порт и эталон разойдутся, расхождение найдёт тест, а не пользователь. Риск не в логике (она проверена), а в том, что её перепишут «по смыслу».
2. ~~Несколько приёмов в день~~ — **решено (v2)**: одна отметка на `(planId, day)` (паритет с ботом); `DaySlot.dose` — суммарная доза за день, `times` — только отображение. Понадобится «утро/вечер» — добавить опциональный `Intake.slotIndex`: старые записи без него остаются валидной отметкой «за весь день», `medplan/1` не меняется.
3. ~~Переносимое окно уведомлений~~ — **решено (v2)**: по данным `constructor.html` окна одинаковы на все дни, сворачиваем на лекарство (`notifyWindow?`, nil = выкл). Вдруг появится план с разными окнами по дням — `medplan/2`, модель заранее не усложняем.
4. **Бюджет 64 уведомлений** при 4+ лекарствах с 30-минутным интервалом не сходится. UX зафиксирован в v2 (разделы 8, 12): настройки показывают «X из 64» на лекарство, при нехватке — сначала увеличить интервал, потом уменьшить горизонт. Риск остаётся только для 4+ лекарств с плотными окнами.
5. ~~Часовой пояс и DST~~ — **решено (v2)**: `startDate`/`stoppedAt` хранятся как `CivilDate` (год/месяц/день, без времени и таймзоны, раздел 3). Номер дня — чистая арифметика гражданских компонент в `Calendar.current`; DST и перелёты на неё не влияют, каждая дата резолвится ровно в один номер дня. Timestamp'ы (`takenAt`) в вычислении дня не участвуют.
6. **Врачебный доступ.** `viewers` + read-only `/stats` в приложении заменяются экспортом. Если врачу нужен постоянный онлайн-доступ — это возвращает к варианту C (бэкенд), который сейчас отклонён. Подтвердить, что PDF/CSV достаточно.
7. **App Store.** Локальные данные, без SDK аналитики → privacy label простой. Риск только по 1.4.1 (раздел 11). Синк через CloudKit добавит метку, но не блокирует.
8. **Судьба бота.** После паритета: снять systemd-юнит и VDS или оставить как резервный канал напоминаний? Второй вариант значит поддерживать два места, где живут данные. Рекомендация — снять.
